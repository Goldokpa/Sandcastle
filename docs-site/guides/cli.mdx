# Govern agents from your terminal

The IdentArk CLI is the operational companion to the control plane. Use it to
register agents, keep credential references out of your repository, and review
human-in-the-loop approvals without giving a production agent raw credentials.

## Install

```bash
pip install identark-cli
identark --version
```

The CLI requires Python 3.11 or later. Pin the version in CI or a deployment
image when you need a repeatable release.

## Sign in

<Steps>
  <Step title="Authenticate with a browser">
    ```bash
    identark auth login
    identark auth status
    ```

    The CLI starts a device-authorisation flow, then stores the resulting
    session in your operating system keychain. It never prints the raw token.
  </Step>

  <Step title="Use a headless machine or CI">
    ```bash
    identark auth login --no-browser
    ```

    For automation, provide a narrowly scoped key at runtime instead of
    persisting one on disk:

    ```bash
    export IDENTARK_API_KEY='csk_…'
    identark agent list
    ```
  </Step>
</Steps>

## Set up an agent project

### First run in five steps

Choose a provider, generate a real sample agent, run it locally, and inspect a
privacy-preserving record of that run:

```bash
identark init --provider openai
pip install "identark[openai]"
export OPENAI_API_KEY='…' # keep this in your shell, never in the project
identark agent run identark_sample.py
identark trail
```

`--provider` accepts `openai`, `anthropic`, or `ollama`. The generated sample
makes one real provider call through `DirectGateway`; it does not use a fake
response or browser simulation. `identark trail` verifies the hash-linked local
record at `.identark/activity.jsonl`. That record contains only timestamp,
provider, model, outcome, and estimated cost—never prompts, outputs, keys, or
credential references—and Git ignores it automatically.

<Warning>
The local activity record is not the governed IdentArk audit trail. DirectGateway
is a local-development helper, so its provider credential is available to the
sample process. Use Gateway Mode for production; then `identark audit list`
shows the authoritative control-plane audit records.
</Warning>

### Promote the sample when you are ready to ship

Connect a normal API-key provider from the terminal. The command uses a hidden
prompt, sends the key directly to the authenticated IdentArk vault endpoint,
and returns only a vault reference. It never accepts the key as a command-line
argument, prints it, or writes it to `.identark/config.toml`:

```bash
identark credential connect openai
# Paste the key twice into the hidden prompt.
```

Then pass the credential **reference**, not the provider key, to the promotion
command:

```bash
identark promote --credential-ref secret/orgs/<org-id>/providers/openai --provider openai
python identark_gateway_sample.py
identark audit list
```

Promotion registers (or reuses) one agent, creates its governed session, and
mints a 15-minute `llm:invoke` capability bound to that agent. The capability
is held in the OS keychain and never written to `.identark/config.toml`; the
generated `identark_gateway_sample.py` uses `ControlPlaneGateway`, so the
provider credential remains outside the agent process.

To make one real governed call immediately, opt in explicitly:

```bash
identark promote --credential-ref secret/orgs/<org-id>/providers/openai --provider openai --run
```

`--run` may incur a provider charge. When it completes, `identark audit list`
shows the authoritative activity record. The capability cannot administer or
read credentials, cannot target another agent's session, and expires
automatically.

### Export independently checkable approval evidence

Once a governed workflow has made HITL decisions, a human account can export a
portable evidence file for an auditor or customer to verify locally:

```bash
identark audit export --output identark-approval-evidence.json
identark audit verify identark-approval-evidence.json
```

### Export risk and policy decision evidence (v2)

For approvals created with decision evidence enabled, export the separate v2
chain to independently check the risk rationale and policy outcome:

```bash
identark audit export --format v2 --output identark-decision-evidence.json
identark audit verify identark-decision-evidence.json
```

V2 links each explanation to a v1 approval hash without changing historical
v1 records. Verify the related v1 bundle separately when both the decision and
its rationale matter. The v2 file contains only numeric risk factors,
categorical indicators, and fingerprinted policy metadata; it excludes request
arguments, prompts, outputs, credentials, capability tokens, and policy source
text.

The bundle has the tool name, risk score, decision, timestamps, and hash links
that the approval chain protects. It excludes tool arguments, prompts, outputs,
provider credentials, and capability tokens. Verification recomputes every
SHA-256 digest locally; it makes no API request.

<Warning>
This proves the integrity and order of records supplied in the bundle. It does
not prove that the exporter included every historical record or independently
attest the bundle's origin. Those stronger claims require a separately anchored
or signed checkpoint.
</Warning>

### Configure an existing project

```bash
identark init
identark credential add OPENAI_API_KEY --ref vault://prod/openai
identark credential scan --strict
```

`identark init` creates `.identark/config.toml`. That file holds project
configuration and references such as `vault://prod/openai` or `env://OPENAI_API_KEY`—never
the credential value itself. Commit the configuration if it is useful to your
team; do not commit a `.env` file containing real secrets.

Register an agent with the control plane when it is ready to be governed:

```bash
identark agent register \
  --name support-agent \
  --provider anthropic \
  --model claude-sonnet-4-5 \
  --credential-ref vault://prod/anthropic

identark agent list
```

## Production boundary

<Warning>
`identark credential inject`, `identark agent run`, and `identark agent dev`
are local-development helpers. They resolve a scalar secret into a child
process environment, so that process can read it. They are not a production
secret-isolation boundary.
</Warning>

For a production agent, use the SDK's `ControlPlaneGateway` or an IdentArk
managed connector. The agent receives a scoped capability and the control plane
enforces policy, records activity, and applies any required approval. See
[Going to production](/guides/production) for the runtime pattern.

```text
CI or operator terminal  →  IdentArk CLI
Production agent         →  ControlPlaneGateway / managed MCP tools
Sensitive operations     →  capability checks + human approval when required
```

## Review high-risk work

```bash
identark approvals list
identark approvals inspect <approval-id>
identark approvals approve <approval-id>
identark approvals reject <approval-id> --reason "Unexpected production change"
```

Approvals require an explicit command. A pending approval expires to **deny**;
the CLI has no auto-approve mode.

## Inspect governed activity

```bash
identark audit list
```

This is a read-only view of the control-plane audit log. It deliberately does
not merge local development records with governed production activity.
